# Git 노선도

## ▶ [여기를 눌러 바로 열기](https://abback-go.github.io/GitMap/)

Git의 브랜치가 어떻게 갈라지고 다시 합쳐지는지를 **지하철 노선도**로 보여줍니다.
설치할 것도, 가입할 것도 없습니다. 링크를 열고 버튼만 누르면 됩니다.

> 커밋은 **역**, 브랜치는 **노선**, 병합 커밋은 두 노선이 만나는 **환승역**입니다.

명지전문대 AI게임학과 강의 자료입니다.

## 처음이라면

오른쪽 위 **▶ 자동 안내**를 누르세요. 설명 말풍선이 따라다니며 커밋부터 브랜치 · 병합 ·
원격 저장소까지 직접 시연해 줍니다. 그냥 두면 저절로 넘어가고, `이전` · `다음`으로
원하는 속도로 볼 수 있습니다.

30단계가 세 장으로 나뉘어 있습니다.

| 장 | 내용 |
|---|---|
| 1부 · 혼자서 시작하기 | 커밋 · 브랜치 · 서버에 올려두기 |
| 2부 · 팀과 주고받기 | 팀원의 커밋 · fetch · pull · PR 병합 · **충돌 해결** |
| 3부 · 정리 | 기호 · 로그 · 학습 시나리오 소개 |

말풍선 아래 **진행 막대의 칸을 누르면 그 단계로 바로 건너뜁니다.** 주소 끝에
`#step=12`처럼 붙여 열면 그 단계부터 시작하므로, 중간에 끊겼을 때 이어보기 좋습니다.

한 바퀴 돌고 나면 **자유 모드**에서 직접 눌러보세요.
잘못 눌러도 `한 단계 되돌리기`와 `처음부터`가 있으니 마음껏 망가뜨려도 됩니다.

## 화면 보는 법

| 영역 | 무엇을 보나 |
|---|---|
| 가운데 노선도 | 버튼을 누를 때마다 선로가 그려집니다 |
| 노선도 위쪽 (내 컴퓨터) | 내 커밋과 브랜치 |
| 노선도 아래 회색 구역 (팀 공용 서버) | **서버에만 있고 내 컴퓨터엔 없는 역**과, 내가 마지막으로 확인한 서버 위치 |
| 현재 위치 (HEAD) | 지금 내가 올라타 있는 브랜치 |
| 명령 | 커밋 · 브랜치 만들기 · 이동 · 병합 · 리베이스 |
| 원격 저장소 (origin) | 팀원이 커밋 · 가져오기(fetch) · 받아오기(pull) · 올리기(push) |
| 실행한 명령 | **진짜 터미널에 칠 git 명령**이 쌓입니다 |

노선도가 가로줄로 **두 구역**으로 나뉘는 게 핵심입니다. 위는 내 컴퓨터, 아래 회색
구역은 팀이 함께 쓰는 서버입니다. `push` · `fetch` · `pull`은 이 경계를 넘나드는
동작입니다.

**역이 어느 구역에 있는지가 곧 "그게 어디 있는 커밋인가"입니다.** 팀원이 서버에만
올린 커밋은 **아래 회색 구역에 파선**으로 그려집니다 — 내 컴퓨터에는 아직 없다는
뜻이죠. `fetch`나 `pull`로 받아오면 **위쪽 내 구역으로 올라오며 진해집니다.**

회색 구역의 `origin/main` 이름표는 **서버의 현재 위치가 아니라 내가 마지막 `fetch`로
확인한 위치**입니다.

마지막 칸이 핵심입니다. 여기 쌓인 명령을 그대로 Git Bash에 옮겨 치면 같은 결과가 나옵니다.
버튼 조작과 실제 명령을 짝지어 익히세요.

`$`로 시작하는 줄을 위에서부터 그대로 옮겨 치면 됩니다. 맨 위 흐린 묶음(`git init` ~
`git push -u origin main`)은 **저장소를 만들 때 한 번만** 치는 것이고, 그 아래가 작업할
때마다 반복되는 명령입니다. `#`으로 시작한 회색 줄은 **팀원이나 GitHub이 한 일**이라
내 터미널에서 칠 명령이 아닙니다. `$`도 `#`도 없는 흐린 줄은 **명령이 터미널에 뿌린
출력**입니다 (`git branch -a`의 브랜치 목록 등).

`git add`(담기)와 `git commit`(저장)이 항상 짝으로 나오는 것도 눈여겨보세요 — 담지 않은
변경은 커밋되지 않습니다. 터미널에서 따라 할 때는 각 `git add .` 앞에서 **파일을 실제로
하나 고쳐야** 담길 것이 생깁니다. 이 도구에서 "무엇을 했나요"에 적는 것이 그 파일 수정에
해당합니다.

## 기호 읽는 법

| 기호 | 뜻 |
|---|---|
| 빈 동그라미 | 보통 커밋 |
| 가운데가 찬 동그라미 | 병합 커밋 (부모가 둘인 유일한 커밋) |
| 회색 **점** 동그라미 | rebase 후 버려진 옛 커밋 |
| 진회색 **파선** 동그라미 | 서버에는 있지만 아직 `fetch`하지 않은 역 |
| 분홍 `HEAD` | 지금 올라타 있는 브랜치 이름표를 가리킴 |
| 속이 빈 이름표 | 서버 띠에 있는 원격 위치 (`origin/main` 등) |

## 이걸로 알 수 있는 것

- `git add`(담기)와 `git commit`(저장)은 **다른 일**이고, 담지 않으면 커밋되지 않는다는 것
- 커밋은 지우는 게 아니라 **쌓이는 기록**이라는 것
- `HEAD → 브랜치 이름표 → 커밋`의 3단 구조. 브랜치를 옮기면 HEAD가 이름표 사이를 이동합니다
- 브랜치를 만든다는 건 **같은 역에 이름표를 하나 더 붙이는 것**일 뿐이라는 것
- 병합 커밋이 생기는 경우와, 새 역 없이 미끄러져 가는 `fast-forward`
- rebase는 커밋을 **복사**해서 해시가 바뀌고, 옛 커밋이 점선으로 남는다는 것
- 원격 저장소: `git push`로 올리고 `git pull`로 받아오는 흐름
- **`fetch`와 `pull`의 차이** — `fetch`는 가져오기만 하고 내 브랜치를 움직이지 않습니다. `pull`은 `fetch` + `merge`
- `origin/main` 이름표는 **서버의 현재 위치가 아니라 내가 마지막으로 확인한 위치**라는 것
- 새로 만든 브랜치는 `git push -u`로 올려야 서버에 생긴다는 것
- `push`가 **거절되는** 상황과 그 뒤처리(`pull` → 다시 `push`), **push한 브랜치에 rebase를 쓰면 안 되는 이유**
- 합치는 일이 **어디서** 일어나는가 — 내 컴퓨터에서 `merge`하면 환승역이 내 쪽에, **서버에서 PR로** 합치면 환승역이 서버 쪽에 생깁니다
- `git clone`으로 이미 있는 저장소를 받아 **다른 PC에서 이어 작업하는** 흐름
- clone해도 **로컬 브랜치는 기본 브랜치 하나만** 생긴다는 것. `origin/develop`이 보여도 `develop`은 없고, `git switch develop`을 하면 그때 **추적 브랜치가 자동으로 만들어진다**는 것

`학습 시나리오` 묶음은 **번호가 배우는 순서**입니다. 앞의 셋은 혼자 하는 일,
`4 Push`부터가 팀 작업입니다.

| 시나리오 | 무엇을 배우나 |
|---|---|
| `1 Commit` | 담기(`add`)와 저장(`commit`)은 **다른 일**이라는 것 |
| `2 Merge` | 브랜치를 갈라 작업하고 **내 컴퓨터에서** 합치기 |
| `3 Conflict` | 같은 파일을 양쪽이 고쳐 **병합이 멈출 때** 푸는 법 |
| `4 Push` | `push`가 **거절될 때** 무엇을 해야 하나 |
| `5 PR` | 합치는 일이 **서버에서** 일어나면 무엇이 달라지나 |
| `6 Clone` | 이미 있는 저장소를 받아 **다른 PC에서 이어 작업하기** |
| `7 Rebase` | 커밋을 **복사**해 옮기기 — 그리고 그 위험 |

`1 Commit`은 입문 첫 주에 모두가 만나는 거절부터 시작합니다. 담지 않고
`git commit`을 눌러 **`nothing added to commit`으로 거절당해 보는** 것이 첫 단추입니다.

`Push`도 마찬가지로 **거절**이 주인공입니다. 내가 커밋하는 사이 팀원이 서버에
올렸을 때 벌어지는 일이죠. 거절은 고장이 아니라 남의 작업을 덮어쓰지 않게 막는
**안전장치**입니다. `git pull`로 합친 뒤 다시 올리면 됩니다.

`PR`은 `Merge`와 짝지어 보세요. 같은 "합치기"인데 `Merge`는 **내 컴퓨터에서**,
`PR`은 **서버에서** 일어납니다. 환승역이 어느 쪽에 생기는지 비교해 보면 차이가
분명해집니다.

`Clone`은 방향이 반대입니다. 시작할 때 내 컴퓨터는 비어 있고 서버에만 저장소가
있습니다 — 역이 전부 **파선**으로 그려진 게 그 표시입니다. `clone`을 누르면 파선이
한 번에 진해집니다. 그 뒤 `origin/develop`은 보이는데 `develop`이 없어 당황하는
지점까지 다룹니다.

맨 앞 `Merge`와 **맨 끝** `Rebase`는 같은 상황을 두 방식으로 처리합니다. 이어서
돌려 보면 무엇이 달라지는지 나란히 비교할 수 있습니다. `Rebase`는 해시가 바뀌고
옛 커밋이 점선으로 남는 등 다루기 까다로워 맨 끝에 두었습니다.
